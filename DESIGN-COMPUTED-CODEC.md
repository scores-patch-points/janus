# DESIGN (a proposal for the owner, khora and Penelope; nothing here is built): the codec is COMPUTED from what we have learned and from givers, not chosen from a discrete registry, for every material
Written 2026-11-20 by the Janus session at its user's direction: "think about how we use codecs to turn everything into EOT; instead of having a discrete codec we should be able to compute it based on what we've learned in the past, along with givers; this applies from language to images". It extends DESIGN-PRONOUN-RULES-BY-GIVER.md (rules by giver, English as a set of codecs, the read-time fold). Statements about what exists were checked on 2026-11-20 against the file named; I have not read khora's image, audio or video adapters, so what they learn and from whom is unverified.

## 1. What a codec is today (checked)
- THE ISTHMUS (khora native/docs/THE-ISTHMUS.md, charter ratified 2026-10-26): material -> decode (its codec) -> EOT -> reason -> EOT -> encode (the target's codec) -> material. A codec is the per-material decode/encode pair. For a language it is its UD grammar (UDTokenizer@1 + UDParser@1 in, UDGrammar@1 out, trained by scripts/train-ud-language.mjs). Khora has adapters for text, image, audio, video, midi, code, math, chat, wikidata and sources, standing on "the same footing".
- So a codec is already a LEARNED object (a parser and measured order parameters trained from a treebank), but it is trained ONCE, offline, from ONE source, frozen into a file, and chosen by a key (an ISO code). `priors/ud-codecs.json` has one entry per language (English = UD_English-EWT only). The choice is discrete and the derivation (which data, which giver, for which context) is not carried by the EOT it produces.

## 2. The proposal: a codec is a function, and every EOT record says which function made it
`codecFor(material, context)` returns a codec COMPOSED at read time from a store of learned evidence and givers, together with its derivation record. The discrete codec of today is the special case where the store holds one source and the context selects it.
1. LEARNED EVIDENCE is data in the log, not weights in a file: append-only entries of kind `codec-evidence` (a source: a treebank release, a corpus, a gold, a correction Penelope's REC made, a detector's labelled output), each with: material, language or modality, variety, period, giver (named), standing (`given` only with a named giver, otherwise `candidate`: the grain theorem), the data's hash, and the counts or tables it contributes (lexicon forms and features, order parameters, marker tables, relation frequencies; for an image: label taxonomy and relation statistics). Learning is a FOLD over these entries, the same as all state here; the past improves the codec because new entries are appended, and a revised entry (REC) changes the fold without rewriting history.
2. GIVERS enter two ways. As SEEDS: a given grammar, standard or taxonomy supplies the initial structure (the UD guidelines' binding principles, a declared label taxonomy), named and scoped. As CONSTRAINTS: a given may forbid what a learned layer would do (a candidate rule cannot override a given one); a learned layer can only ADD candidates, refute a given only by showing a counterexample (the refutation is evidence for the giver's revision, not a silent override).
3. COMPOSITION at read time. Context is whatever is known about the material (declared variety, date, genre, modality) and whatever the material shows (a first pass reads its own features). Two ways to compose, to be measured against each other, not assumed:
   (a) ENSEMBLE: decode with each selected source's codec and keep ALL records as layers with weights (EOT already folds out at the face wanted; layers are the unit, and agreement across independent sources is standing: DESIGN-EVA-PATTERN-STANDING.md);
   (b) BLEND: pool the counts and tables of the selected sources with the weights and train or recompute one decoder, cached by its derivation hash.
   The default face ("standard English") is a declared fold of the distribution, computed on read with its sources named, never the one stored truth.
4. THE DERIVATION RECORD travels with every EOT record: `CodecDerivation@1 = { material, context, sources: [{ id, giver, scope, weight, standing, dataHash }], composed: hash, gaps }`. Any reading can be audited and re-derived; two records of the same text from different derivations are two layers, not a conflict. A context for which no source has scope yields the typed gap `no_codec_source`, never another language's or period's codec and never an English hub (the Isthmus's own rule).
5. THE SAME ENVELOPE FOR EVERY MATERIAL. Only the sources and the decode differ: language (treebanks, grammars, corrections), image (a detector or captioner's labelled output with its taxonomy as a giver, plus relation statistics learned from past images), audio (phonemic or lexical priors), midi, code (the language's grammar). Each yields EOT content nodes and cube-addressed relations; the record format of the derivation is the same.

## 3. Where each part lives (no repo imports another)
khora: the adapters (decode and encode) and the learned-state fold over `codec-evidence`. Janus: the codec door (`nl-eot.mjs` `loadGrammar`) becomes `codecFor`, structure only; it writes no rules and no verdicts. Penelope: givers' declarations as DEF·Pattern priors, standing `given`, and the judgement (EVA) of whether a composed codec's layers agree and the revision (REC) when a source is refuted. The registry file (`ud-codecs.json`) becomes the seed list of sources, not the choice.

## 4. What would show it works, and what would sink it (to pre-register, not run)
- Computed against discrete: on held-out text of each variety (EWT-like web text, GUM-like multi-genre), is the composed codec at least as good as the best single-source codec of the matching variety, and better on a mismatched variety? Twin (rule 3): the same composition with source weights shuffled and with provenance labels shuffled; if the twin matches it, the context selection is decoration.
- Ensemble against blend, each against the single source, with the cost of each stated.
- Learning from the past: appending corrections and gold entries changes the fold in the right direction on later documents and does not on documents the entries were not about (a target-swap control); an entry written from a test split must be impossible (the log's split labels refuse it).
- Failure modes to name in advance: composition averages incompatible annotation conventions across treebanks into a worse parser; learned layers launder themselves into `given`; the default fold hides that it is an English hub; the derivation record is dropped by a consumer. Each gets a guard: a convention-compatibility check before pooling, a refusal to write standing `given` without a named giver, a test that no code path falls back to English, and a test that an EOT record without a derivation is refused by the door.
- First runnable step with what we hold: English, two sources (EWT, and GUM which khora's evaluation already reads), the pronoun-rules task of DESIGN-PRONOUN-RULES-BY-GIVER.md as the measure; a download of any further treebank needs the owner's word with its source and size named.
